The Python continuation implements a bounded version of the flow in [data/notes.md](../data/notes.md): description → candidate characteristics → KTRU compatibility → missing fields, extras and clarification. It uses the existing Nimble deployment and standard-library code; no notebook kernel or local model is needed.

The important distinction in the notes is between making decisions and generating structure. The current server accepts a supplied `state` and `choice` questions. It does not provide a documented tool-execution loop or arbitrary argument generation. Python can nevertheless produce structured output: construct the options, ask Nimble to choose, collect the selected facts/spans, and run the catalog checks. Calling an option an action would not itself execute a tool or extract a previously unseen value. Free numeric values come from spans in the input, rather than enumerating all possible numbers.

| Stage | Python's work | Nimble's work | Explanation in output |
|---|---|---|---|
| Product retrieval | Tokenize the leading product phrase and rank catalog names by weighted overlap | None | Query phrase, shared tokens, scores, shortlist truncation |
| Product relevance | Group candidate names into questions | Check whether each name describes the actual product | Full status distribution; unsupported names cannot produce a provisional code |
| Categorical extraction | Enumerate the shortlisted positions' categorical vocabulary | Classify each fact as supported, contradicted, unknown or conflicting | Values, statuses, probabilities, catalog sources; categorical evidence spans remain unverified |
| Numeric extraction | Parse exact values, offsets, units and deterministic conversions | Choose which compatible span actually describes a particular product property | Original span and normalized value/OKEI |
| Constraint checks | Compare allowed categorical values and numeric exact/interval rules, preserving open bounds | None | Matches, conflicts, unknowns and missing required fields |
| Extras and clarification | Preserve unbound measurements and explicit user fields; apply additional-field policy; choose a distinguishing/missing-field question | None | Per-candidate extra actions and a next question |

Retrieval happens before exhaustive categorical checking to bound model work. The existing saved runs take about 10–14 seconds for a 20-fact drill family. Applying that rate to 2,568 facts gives a rough 22–30 minutes per input. That estimate supports testing a shortlist; it does not establish its recall. The default searches the entire exploratory three-domain snapshot, rather than assuming every input is a drill. `--scope drills` is useful for reproducing the initial family experiment.

The first dry run found a concrete weakness in unrestricted word-overlap retrieval: “без ударного режима” ranked “Клеймо ударное” above drills. The baseline now stops the product phrase at accessory/property clauses (`с`, `без`, `из`, `для`, semicolons and pipes), and a separate model question checks the candidate's full product name. Another dry run showed several versions of the same jacket or chair occupying most of the shortlist. Retrieval now interleaves distinct names before selecting further codes/versions of each name, preserving every selected record's identity. This is still a simple lexical heuristic: unusual phrasing, typos, synonyms and multi-product descriptions need a reviewed retrieval benchmark. The constraint engine cannot repair a candidate that retrieval missed.

Missing information never means false. A battery fact can exclude a mains-only position. A missing battery voltage leaves a required field unresolved. Multiple incompatible supported values for a single-valued property remain uncertain instead of eliminating every code. A numeric value is applied only after ownership is selected above the experimental threshold. A charger's 220 V must not become the drill's battery voltage. Signed values, bounds and interval endpoints are retained for review rather than used as exact point values.

For the drill example, existing categorical evidence distinguishes battery from mains power. It does not complete the battery drill's required specification: chuck minimum/maximum diameters, maximum RPM and battery capacity remain missing; voltage also needs ownership binding. The script therefore produces explained compatibility and a clarification request. Even if every implemented check passes, `final_code` remains empty until lifecycle, product relevance, verified categorical evidence and remaining application rules are validated. A provisional code is explicitly restricted to the retrieved shortlist.

Extras have two different origins. Unbound measurements are original input spans whose ownership is unknown, so they cannot yet be declared product extras. `--extra NAME=VALUE` records a user-supplied property. Per candidate, forbidden additions get `do_not_add`; permitted additions get `review_before_add`; missing policy gets `additional_field_policy_unknown`. Existing catalog names get `map_and_validate`. This preserves the information without claiming a complete extractor for arbitrary free-text properties or an automatic SPGZ crosswalk.

The follow-up suite tests the observed failures before changing thresholds. Six numeric cases are repeated with raw versus raw-plus-normalized candidate descriptions. Input, instructions, choices and labels stay identical; only numeric representations change. Seventeen fact checks span tools, furniture and clothing, including missing values, negation, packaging, explicit correction and unresolved contradictions. Report supported precision and unsupported additions separately from aggregate accuracy: many correct “unknown” answers can hide an invented positive fact. All examples are labeled development fixtures; they do not measure final KTRU accuracy on real procurement inputs.

Offline validation covers unit normalization, open/closed bounds, unknowns, conflicts, object relevance, additional-field policy, partial runs and exact-request replay. Saved model results can be replayed with `--replay`, but a categorical-only run cannot stand in for the new name or numeric questions. An incomplete replay is marked explicitly. Test fixtures use a fake client solely to verify control flow and artifact persistence; those outputs are never reported as model accuracy.
