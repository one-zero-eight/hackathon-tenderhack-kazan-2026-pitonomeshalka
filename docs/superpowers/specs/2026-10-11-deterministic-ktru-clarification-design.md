# Детерминированное уточнение до конечного кода КТРУ

Дата: 2026-10-11

## Зачем

Текущий `/analyze` возвращает список `uncertain`-кандидатов и текстовую подсказку, но не даёт пользователю ответить и не выдаёт конечную карточку. В кейсе аккумуляторной отвёртки классификатор не подтверждает синонимию названия, поэтому все позиции остаются неопределёнными.

Цель — превратить результат `needs_clarification` в короткий интерактивный путь до выбранного конечного кода без LLM и без повторного вызова embedding/classifier.

## Основной сценарий

1. `/analyze` сохраняет обычный результат.
2. Если осталось несколько нерRejected-кандидатов, backend строит структурированный вопрос:
   - сначала неразрешённая разделяющая характеристика семейства КТРУ, если её варианты действительно делят кандидатов;
   - иначе вопрос о виде товара с названиями оставшихся позиций.
3. Пользователь выбирает один из вариантов.
4. `POST /clarify` проверяет, что вопрос принадлежит исходному прогону, и пересекает текущее множество кодов с `candidate_codes` выбранного варианта.
5. Если остался один код, backend возвращает `final_card` с кодом, версией, названием и полной схемой характеристик позиции КТРУ.
6. Если осталось несколько, строится следующий вопрос. Лимит — 3 раунда; после него показывается прямой выбор из оставшихся позиций.
7. Вариант «Ничего из перечисленного» не выбирает код: backend возвращает `suggest_expand=true`, а frontend предлагает запустить новый `/analyze` с увеличенным `top_k`.

## Источник вопросов

Только данные текущего прогона и справочника КТРУ:

- `detected_families[].splitting_characteristics[].options[].children` — разделяющие характеристики и соответствующие дочерние коды;
- `candidates[]` — названия и коды позиций для прямого вопроса о виде товара;
- `ktru_position.characteristics` — полная финальная карточка.

Никакая модель не генерирует вопросы, варианты, код или обоснование.

## Состояние

Состояние уточнения хранится как `run_artifacts` с именем `clarification_state.json`:

```json
{
  "round": 1,
  "candidate_codes": ["..."],
  "question_id": "...",
  "answers": [{"question_id": "...", "option_id": "..."}]
}
```

Исходный `analysis_runs.result` остаётся неизменным доказательством первичного анализа. Каждый `/clarify` идемпотентно пересобирает публичный ответ из исходного результата и текущего artifact.

## API

`AnalysisResponse` получает необязательные поля:

- `clarification: Clarification | null`;
- `final_card: FinalCard | null`;
- `suggest_expand: bool`;
- `manual_choice: bool`.

`POST /clarify`:

```json
{"run_id":"...", "question_id":"...", "option_id":"..."}
```

Ответ — обновлённый `AnalysisResponse`.

## Финальная карточка

`FinalCard` содержит:

- код, версию, наименование, статус и период действия;
- единицу позиции;
- `characteristics[]`: код/название, обязательность, тип выбора, числовой признак, единица и все допустимые значения/диапазоны;
- короткое детерминированное обоснование: пользователь выбрал вариант вопроса и тем самым сузил множество до данного кода;
- `requires_review=true`: выбор конечный для пользовательского сценария, но юридическая применимость и жизненный цикл требуют проверки.

## Ограничения

- Максимум 3 разделяющих вопроса.
- Ответ только выбором из вариантов; свободного текста нет.
- Категория не меняется автоматически.
- Нет новых модельных/внешних вызовов после `/analyze`.
- Если исходный shortlist не содержит нужный товар, пользователь явно запускает расширенный поиск.
