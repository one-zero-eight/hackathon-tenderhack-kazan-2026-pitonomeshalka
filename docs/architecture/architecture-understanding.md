## 0. Главное ограничение — читать раньше всего остального

Три факта определяют, что этот проект делает, а чего **не** делает. Они вынесены наверх намеренно, чтобы их нельзя было потерять в дальних таблицах.

1. **Система не выдаёт итоговый код КТРУ.** Подробный отчёт всегда фиксирует `final_code: None` (`backend/src/pipeline.py:378`), публичный контракт — `requires_review: Literal[True]` (`backend/src/schemas.py:103`), то есть поле буквально не может принять другое значение. Есть только `recommended_candidate` — **предварительный** `code@version`. Это прямо расходится с формулировкой брифа «поэтапно сужает множество категорий КТРУ … **до конкретного итогового конечного кода**».

2. **Диалог сужения не является диалогом.** `/analyze` не имеет сессии: каждый вызов — новый прогон с нуля. Ответ на уточняющий вопрос нужно **вручную вписать в текст** и отправить заново. Пользовательские `extras` помечаются действием (`map_and_validate`, `review_before_add`, …), но **не** подаются в проверки и **не** закрывают обязательные поля (`backend/src/pipeline.py:316-322`, `:569`). Бриф требует «поэтапного сужения при вводе характеристик» и «предложить конкретные шаги» — реализовано только текстовое `clarifying_question`.

3. **Свежий checkout не запускается документированным способом.** ETL ожидает `data/ktru/*.xml`, `data/xlsx/*.xlsx` и `data/КТРУ/КТРУ`, но на диске их **нет**: реальные данные лежат в `data/Казань 2026/…` (184 ZIP-архива, 3 XLSX). Каталог `seeds/` тоже отсутствует, поэтому `scripts/db_seed.sh restore` не работает. Плюс тесты бекенда в `main` **не импортируются** (раздел 12).

Дальше — полное описание того, что при этих ограничениях построено и работает.

## 1. Резюме

Проект решает задачу хакатона «Автозаполнение ключевых характеристик в СТЕ»: по свободному русскоязычному описанию товара найти подходящие позиции справочника **КТРУ** (Каталог товаров, работ и услуг ЕИС), извлечь и унифицировать характеристики с единицами измерения, объяснить противоречия и сказать, чего не хватает.

Реализован **одноразовый консультативный анализ**, а не интерактивный мастер подбора кода:

```
описание → гибридный поиск кандидатов → пакет вопросов NLI-классификатору
         → детерминированная проверка правил каталога → объяснённые кандидаты + один вопрос
```

Ключевое архитектурное решение — **разделение труда между моделью и кодом**. Модель (`jiwo-4b` через «System One» API) только выбирает из **заранее подготовленных Python'ом вариантов** и возвращает вероятности. Всё, что связано с числами, единицами, диапазонами, обязательностью и допустимыми значениями, считается детерминированным кодом. Модель не генерирует структуру и не выполняет действия — она скорит гипотезы. Это осознанный выбор, зафиксированный в `experiments/pipeline-explanation.md` и `experiments/README.md` §4.

Второе ключевое решение — **тотальная наблюдаемость**: каждый исходящий запрос к модели коммитится в БД **до** отправки, поэтому прерванный или зависший вызов остаётся видимым (`backend/src/service.py:115-116`).

Стек: Python 3.13 / FastAPI / SQLAlchemy 2 / PostgreSQL 17 + pgvector + pg_trgm / Redis 7 / Vue 3 + TypeScript + Vite + Tailwind v4 + PrimeVue 4 / Docker Compose / nginx. Всё в Linux, платные поисковые API и проприетарные LLM не используются — ограничения брифа соблюдены по составу технологий.

Объём кода: ~6 100 строк Python (бекенд + скрипты + эксперименты), ~3 460 строк TS/Vue (из них ~40 % — тесты).

## 2. Бизнес-контекст

Источник: `data/Казань 2026/Презентация Задачи_Хакатон_Казань_20261009_1900_pdf.pdf` (извлечённый текст), `docs/implementation-plan.md`. **confidence: high** (документ организаторов).

### 2.1 Проблема

КТРУ приводит описание закупаемых товаров к единому стандарту, чтобы уменьшить разнобой формулировок у разных заказчиков. Позиция КТРУ задаёт код, наименование, связь с ОКПД2, характеристики, допустимые значения и диапазоны, единицы измерения, статус и период действия, связи с родительскими/укрупнёнными позициями. Специалисту по закупкам нужно вручную сопоставить свободное описание товара с этой структурой — трудоёмко и ошибкоопасно.

### 2.2 Что требует бриф

| Требование | Источник |
|---|---|
| Ввод описания на естественном языке, **включая опечатки и неполные данные** | слайд «Пользователь… 1)» |
| Унифицированные характеристики + сопоставленные значения и единицы | там же |
| Итоговый код КТРУ | там же |
| **Видеть поэтапное сужение** множества кодов при вводе характеристик | слайд «Пользователь… 2)» |
| Уведомление о невозможности однозначно определить КТРУ + **конкретные шаги** по исправлению | там же |
| Распознавание ошибок в характеристиках (опечатки, явные несоответствия, несуществующие значения) **с обоснованием** | слайд «Пользователь… 3)» |
| Видеть, что унифицировано, что сопоставлено, **в реальном времени** | слайд «Пользователь… 4)» |
| Удобный веб-интерфейс | «Ключевые задачи» |
| Тестирование на реальных кейсах, включая неполные/некорректные данные | там же |
| Возможность масштабирования | там же |
| **Схема реализации в нотации BPMN** для защиты | «Этапы защиты» |

### 2.3 Ограничения

- Linux + веб-интерфейс.
- Запрещены платные поисковые API (Yandex Search API, Google Custom Search JSON API).
- Запрещены внешние API **проприетарных** LLM (OpenAI GPT, Google Gemini, Anthropic Claude и подобные).
- Запрещены low-code/no-code платформы.
- Разрешены только **открытые** ML-модели, суммарный VRAM на инференс ≤ **40 ГБ**; предпочтение лёгким и быстрым решениям; необоснованно тяжёлые модели снижают оценку.
- Допускаются роутеры LLM (timeweb, selectel), предпочтение отечественным.

### 2.4 Категории и данные

Категории хакатона: **одежда, мебель, инструменты**. Превалирующий источник — справочник КТРУ, его характеристики и значения. Анализируются `nsiKTRUNew_all-actual_*.xml`; `…_not-actual_…` игнорируются. Приложены три выгрузки XLSX (фактические характеристики СТЕ либо типовые свойства по категориям).

Фактические объёмы на диске: 184 ZIP с XML КТРУ + 3 XLSX (`Инструменты` 13 МБ, `Мебель` 18 МБ, `Одежда` 19 МБ), всего ~298 МБ. **confidence: high** (наблюдение файловой системы).

## 3. L0 — Бизнес-возможности

Четыре возможности, которые продукт должен давать. Статус — по коду `main`.

| ID | Возможность | Статус | Обоснование |
|---|---|---|---|
| `cap.interpret` | Интерпретировать свободное описание товара: свойства, значения, единицы, числа | **реализована частично** | `properties` в ответе; числа — только точечные и только 4 единицы (R7) |
| `cap.narrow` | Сужать множество позиций КТРУ до конкретного кода | **не реализована** | `final_code` всегда `None`; есть только `recommended_candidate` |
| `cap.explain` | Объяснять вердикт: почему кандидат подходит/отклонён, чего не хватает, какой вопрос следующий | **реализована** | `reasons`, `missing_required`, `warnings`, `clarifying_question`, `detected_families` |
| `cap.detect-errors` | Находить ошибки ввода (опечатки, несоответствия, несуществующие значения) с обоснованием | **реализована частично** | Опечатки — LanguageTool на фронте; несоответствия — правила каталога; отдельного «несуществующего значения» как класса ошибки нет (R6) |
| `cap.batch` | Массовая проверка таблицы описаний | **реализована** | CSV-вкладка, последовательный прогон со стримингом результатов |

Отдельная, не заявленная в брифе, но фактически сильная возможность — **воспроизводимость и аудируемость**: каждый прогон сохраняет исходный запрос, план, точные исходящие JSON-запросы к модели, ответы, тайминги и ошибки (раздел 8.2).

Лексический fallback частично закрывает эмбеддинги, но не классификатор.

## 7. Доменная модель и данные

### 7.1 Ключевые понятия

Три вещи намеренно различаются (`experiments/README.md` §2). Это ядро предметной модели, и код его соблюдает.

| Термин | Пример | Смысл |
|---|---|---|
| **Характеристика** | `Тип питания` | Свойство, которое можно описать |
| **Факт о товаре** | `Тип питания = От аккумулятора` | Утверждение о конкретном товаре пользователя |
| **Правило каталога** | «эта позиция допускает питание от аккумулятора» | Условие, против которого проверяется факт |

Критическое следствие, зашитое в логику: **значения каталога — это разрешения, а не утверждения**. Если позиция допускает и «Да», и «Нет» для реверса, это не значит, что у товара оба. Поэтому опровергнутая гипотеза **не** исключает позицию автоматически (`experiments/README.md` §8, `backend/src/pipeline.py:395-414`).

### 7.2 Идентичность

| Сущность | Идентичность | Доказательство |
|---|---|---|
| Импорт каталога | `sha256` от манифеста исходных файлов | `scripts/load_db.py:56`, `models.py:43-49` |
| Позиция КТРУ | `(import_sha256, code)` в БД; бизнес-идентичность — `(code, version)` | `models.py:117-119`; `docs/implementation-plan.md` M2 |
| Характеристика | `(import_sha256, position_code, code)` | `models.py:159-161` |
| Значение | суррогатный `id` + `UNIQUE(import_sha256, position_code, characteristic_code, ordinal)` | `models.py:195-201` |
| Гипотеза (факт) | `sha256(normalize(name), canonical_value, okei)[:20]` | `classifier_experiments.py:55-56`, `pipeline.py:162-165` |
| Прогон анализа | `run_id` = UTC-таймстамп `%Y%m%dT%H%M%S%fZ` + `_` + uuid4 hex | `service.py:141`, валидируется regex'ом в `routes.py:200` |
| Конфиг эмбеддингов | fingerprint от `{model, dimensions, query/document prompts, document_format}` | `backend/src/retrieval.py:13-17` |

Идентичность гипотезы намеренно **не** включает контекст позиции: имя характеристики — «подсказка для извлечения, а не идентичность» (`pipeline.py:167`). Поэтому параллельно ведётся `scoped_hypotheses` с ключом `((parent_code, parent_version), char_code, normalized_name, okei)` — один и тот же факт проверяется один раз, но применяется в правильной области.

### 7.3 Две схемы PostgreSQL

Разделение принципиальное: `PostgresStore` **запрещает** совпадение схем доказательств и каталога (`storage.py:55-56`) и транслирует логическую схему `catalogue` через `schema_translate_map` (`storage.py:64`), что позволяет тестам создавать изолированные схемы.

**Схема `catalogue`** (миграции 002, 003) — данные каталога:

| Группа | Таблицы |
|---|---|
| Снимки и provenance | `catalogue_imports`, `catalogue_sources`, `source_files` |
| КТРУ | `ktru_position`, `ktru_characteristic`, `ktru_value` |
| Справочники | `okei`, `okei_alias`, `okpd2` |
| СПГЗ/КПГЗ/СТЕ | `kpgz`, `kpgz_characteristic`, `kpgz_value`, `kpgz_characteristic_ref`, `spgz_ref`, `spgz_ref_value`, `workbook`, `ste` |
| Векторы | `embedding_configs` + колонки `embedding`/`embedding_config` на трёх уровнях КТРУ |
| Производные | view `ktru_domain`, **materialized view** `ktru_family_splits` |

Индексы: **HNSW** `vector_cosine_ops` на `ktru_position`, `ktru_characteristic`, `ktru_value`; **GIN trgm** на `catalogue.norm(name)` / `norm(text)` для тех же трёх; плюс `okpd2`, `parent_code`, `(import_sha256, parent_code, parent_version, code)` для семейств. Функция `catalogue.norm(t)` = `btrim(regexp_replace(replace(lower(t),'ё','е'),'\s+',' ','g'))` — нормализация определена **в БД**, чтобы индекс и запрос использовали одно определение (`002_catalogue.sql`).

Материализованное представление `ktru_family_splits` (003) — самая интересная часть модели. Оно заранее вычисляет, **какие характеристики различают дочерние позиции одного родительского шаблона**: группирует детей по «сигнатуре домена» (choice + is_numeric + набор нормализованных значений/диапазонов) и оставляет только те характеристики, где сигнатур больше одной **или** покрыты не все дети. Комментарий в представлении фиксирует принцип: «Snapshot-only domains; eligibility is evaluated by the reader, not cached» — то есть кэш не подмешивает политику актуальности, её считает читатель. `REFRESH` выполняется один раз внутри транзакции импорта (`load_db.py:82-84`).

Ограничения целостности заслуживают отдельного упоминания — они кодируют предметные правила на уровне БД:

```sql
CHECK (text IS NULL OR spans IS NULL)                     -- значение либо текстовое, либо числовое
CHECK (text IS NOT NULL OR spans IS NOT NULL OR issue IS NOT NULL)  -- пустых значений не бывает
CHECK (spans IS NULL OR (array_ndims(spans)=1 AND cardinality(spans)>0
        AND array_position(spans,NULL) IS NULL
        AND NOT ('empty'::numrange = ANY(spans))))         -- диапазоны валидны
CHECK ((embedding IS NULL) = (embedding_config IS NULL))   -- вектор без конфига невозможен
CHECK (parent_version IS NULL OR parent_code IS NOT NULL)
```

`ktru_value.spans` — `NUMRANGE[]`, сохраняющий **открытость/закрытость границ** каждого интервала; комментарий в 002 поясняет: «All points/ranges in one XML value; malformed groups are NULL with original XML in issue». То есть нераспознанное значение не выбрасывается, а quarantined с сохранением исходника.

**Схема `public`** (миграция 001) — доказательства и служебные данные:

| Таблица | Содержимое |
|---|---|
| `analysis_runs` | Исходный запрос, план, счётчики, статус, ошибка, подробный `analysis` и компактный `result`; FK `catalogue_import_sha256` для воспроизводимости |

| Объект | Состояния | Где определено |

Параметр `as_of` в сигнатуре есть, но вызывающий код его не передаёт (`storage.py:27`, `:124`, `:202`). **confidence: high**, риск R8.

## 8. L4 / E2E — основной бизнес-путь

Диаграмма: [`analyze-flow.dot`](analyze-flow.dot). Все шаги ниже подтверждены кодом; **confidence: high**, если не указано иное.

### 8.1 Путь «текстовый поиск»

**Шаг 1 — ввод и орфография (только UI).** Пользователь печатает описание в `textarea` (лимит 10 000 символов на фронте и на бэке). `watch(text)` запускает дебаунс-проверку через LanguageTool. При находках появляется `CorrectionsPanel` с кнопками «применить одно» / «применить все».

> По правилам разделения UI- и бэкенд-доказательств: **подтверждено**, что UI предлагает исправления и подставляет их в текст. **Не подтверждено**, что исправленный текст как-то влияет на бэкенд иначе, чем обычный текст — бэкенд LanguageTool **не вызывает вообще** (`backend-review.md`, gap 5). Орфография — исключительно фронтовая забота.

Token-guard в `useSpellcheck.ts:29,47,50` отбрасывает устаревшие ответы: если пользователь продолжил печатать, результат старой проверки не затрёт новую.

**Шаг 2 — отправка.** `POST /api/analyze` через nginx → `backend:8000/analyze`. `proxy_read_timeout 600s` (`frontend/nginx.conf:23`) — потому что прогон может идти минуты.

**Шаг 3 — захват блокировки.** `model_lock.acquire(blocking=False)`; при неудаче `ModelBusy` → **503 + `Retry-After: 5`** (`service.py:139-140`, `app.py:23-28`). Блокировка **process-wide**: один инстанс бекенда = один одновременный анализ.

**Шаг 4 — регистрация прогона.** `run_id` = UTC-таймстамп + uuid4; `begin_run` пишет строку `analysis_runs(status='running', request=jsonb)`. `current_run` (ContextVar) связывает последующие embedding-вызовы с этим прогоном (`storage.py:20`, `service.py:142`).

**Шаг 5 — поиск кандидатов.** `EmbeddingRetriever.retrieve` (`retrieval.py:42-80`):

1. `get_active_import(KTRU_CATALOG_KEY)` — какой снимок каталога активен. Если нет → `ValueError` → 422/503.
2. `has_embeddings(import_id, fingerprint)` — есть ли вектора **именно этой** конфигурации. Если да — запрос эмбеддится через meow-embed (768 измерений, иначе ошибка), и поиск становится гибридным. Если нет — остаётся лексический, и это честно пишется в метаданные.
3. `search_catalogue` (`storage.py:200-283`) — ядро поиска, см. 8.3.
4. `get_family_splits` + расширение братьями: если кандидат имеет родительский шаблон, в выборку **добавляются его братские позиции**, даже если поиск их не нашёл — при условии, что общий объём не превысит `top_k` (`retrieval.py:58-65`). Это прямой ответ на проблему «характеристики не различают коды, различие в именах/семействе» из `characteristic-first-feasibility.md` (кейс 2: стул на деревянном и металлическом каркасе).
5. Недостающие позиции догружаются `get_positions`; для добавленных братьев синтезируется evidence `method: "family_sibling"`.

**Шаг 6 — подготовка плана.** `pipeline.prepare` (`pipeline.py:144-244`) строит три типа вопросов:

| Тип | Что спрашивается | Идентификатор |
|---|---|---|
| `pipeline_product` | «Вид самого товара = \<название\>» — по одному на **уникальное нормализованное имя** | `product_<hash>` |
| `pipeline_facts` | Категориальные гипотезы чанками по `chunk_size` (1–8) | `fact_<hash>` |
| `pipeline_numeric` | «Какой из найденных числовых фрагментов задаёт свойство X самого товара» + варианты `unknown` / `conflicting` | `measurement_<hash>` |

Числовые фрагменты извлекаются regex'ом `MEASURE` (`classifier_experiments.py:282`): поддерживаются `кВт/кВ/Вт/В/мм/см/м/А·ч` с конверсией в базовые единицы и кодом ОКЕИ (`212/222/003/263`). Функция `scalar_span` (`pipeline.py:134-141`) **отсекает** фрагменты, которые не являются точечным наблюдением: границы диапазонов, знаки `±`, «не менее/более», «от…до», `< > ≤ ≥ ≈`. Такие измерения остаются для ревью, а не молча превращаются в «ровно 18 В» — это ровно то место, где наивная реализация ломается («зарядное устройство от сети 220 В» не должно стать напряжением аккумулятора дрели).

Если план требует больше `BACKEND_MAX_QUESTIONS` (128) вопросов — `ValueError` → **422 без единого вызова модели** (`pipeline.py:242-243`).

**Шаг 7 — батчинг.** `batch_jobs` пакует независимые вопросы в HTTP-запросы по `CLASSIFIER_BATCH_SIZE` (16 по умолчанию; 0 отключает). ID вопросов неймспейсятся во избежание коллизий, потом отображаются обратно. Замер 2026-10-10: те же 61 вопрос — 4 запроса вместо 19, время классификатора 7.56 с против 16.05 с, все выбранные ответы совпали, максимальная разница вероятностей 0.00124 (`backend/README.md`, `docs/implementation-plan.md`). Батчи отправляются **последовательно**.

**Шаг 8 — вызовы модели с предотправочным коммитом.** Для каждого батча: `start_model_call` коммитит исходящий payload **до** `client.infer(...)`, затем `finish_model_call` (`service.py:107-131`). Комментарий в коде объясняет зачем: «Commit before dispatch: interrupted or still-running GPU calls stay visible». При ошибке — `break`, **без ретраев**: «Never retry a timed-out call: it may still own the shared GPU».

`ClassifierClient.infer` (`classifier_experiments.py:199-221`) валидирует ответ: совпадение модели, совпадение множества ID вопросов, совпадение набора вариантов с критериями, конечность вероятностей в [0,1], сумма = 1 (±1e-5), выбранный вариант действительно максимален. Это защита от протокольных сбоев; **истинность ответа она не устанавливает** — что прямо задокументировано.

**Шаг 9 — детерминированная проверка.** `pipeline.analyze` (`pipeline.py:495-624`):

- `accepted(answer, choice, threshold)` — ответ засчитывается, только если выбор совпал **и** его вероятность ≥ `threshold` (0.8 по умолчанию, **не откалиброван**).
- Продуктовая идентичность: `supported` → кандидат может стать `compatible`; `contradicted` → `rejected`; иначе `uncertain`.
- `categorical_rule` (`pipeline.py:395-414`): противоречие или несколько `supported` для `one_of` → `unknown` («Неоднозначные значения»); подтверждённое значение вне списка допустимых → `conflict` (или `unknown`, если сами правила каталога повреждены); подтверждённое значение из списка → `matched`.
- `product_numeric_check` (`pipeline.py:268-272`) + `numeric_rule` (`:247-265`): принадлежность точки объединению интервалов значения **с учётом включённости границ**, через `Decimal`. Если хоть одна альтернатива дала `None` (битое правило) — результат `unknown`, не `conflict`.
- Обязательные поля: `char.required and not covered` → в `missing_required`.
- `unmatched` — подтверждённые гипотезы, отсутствующие в схеме кандидата: «absence is not automatically a contradiction».
- `extras` → `extra_action` по флагу `no_new_features` (`pipeline.py:316-322`).
- `resolve_families` (`pipeline.py:417-492`) — см. 8.4.

**Шаг 10 — вердикт.** `recommended` выдаётся только если: ровно один `supported`, инференс полон, нет недостающих обязательных полей, нет отсутствующих родительских версий, нет неразрешённых противоречий, нет `uncertain`-альтернатив, нет неразрешённых семейств и нет вопроса-различителя (`pipeline.py:600-602`). Иначе `None`. Затем дерево статусов (`:603-622`) в порядке: `retrieval_miss` → `incomplete_inference` → `no_compatible_shortlist_candidate` → `needs_clarification` (семейства) → `needs_clarification` (родитель) → `needs_clarification` (противоречия) → `ready_for_review` → `needs_clarification` (вопрос по обязательному полю).

Порядок ветвей содержателен: **неполный инференс важнее отсутствия кандидатов** — потому что «отсутствующие ответы нельзя считать отрицанием» (`pipeline.py:607`).

**Шаг 11 — сохранение и ответ.** `finish_run` пишет `analysis` (подробный снимок) и `result` (компактный публичный ответ). При ошибке модели — `InferenceFailure(message, result)` → **502 с частичным результатом внутри** `detail.result`, включая его `run_id`, чтобы ответ можно было позже дочитать через `/results/{run_id}`.

**Шаг 12 — отображение.** `AnalysisResult` → `CandidateBlock` (статус-чип, причины, Недостающие поля) + `PropertiesTable`. Кандидаты отсортированы `compatible → uncertain → rejected`, внутри — по коду и версии (`presentation.py:17-18`).

После завершения (`searchPhase` = `done` или `error`) фронт сохраняет запрос в историю: `POST /history` → Redis `LPUSH`+`LTRIM`+`EXPIRE`, и перечитывает её. Ошибки истории глушатся — «history is best-effort» (`TextSearchPanel.vue:57-67`).

### 8.2 Путь «восстановление потерянного ответа»

Отдельный, хорошо продуманный сценарий. `/analyze` выполняется в worker-потоке и **продолжается после отключения браузера**; отмена инференса не реализована. Если браузер не получил ответ (таймаут, прокси, перезагрузка), пользователь берёт `run_id` из логов (`Analysis started: run_id=…` / `Analysis saved: run_id=…`) и вызывает `GET /results/{run_id}` — чтение **только из PostgreSQL**, без обращений к моделям, доступно пока классификатор занят (`routes.py:191-227`). `404` означает «прогон неизвестен **или ещё считается**».

Это осознанный компромисс синхронной архитектуры, и он задокументирован вместе с диагностикой (включая объяснение, почему `TypeError: NetworkError` в Swagger ничего не diagnostирует и почему keep-alive timeout Uvicorn не продлевает активный запрос).

### 8.3 Как устроен гибридный поиск

`search_catalogue` (`storage.py:200-283`) — самый технически плотный участок. Для каждого из трёх полей (`position.name`, `characteristic.name`, `value.text`) и каждого режима выполняется отдельный ранжированный запрос:

| Поле | Режимы |
|---|---|
| `position` (имя товара) | `lexical` (`similarity` + `%`), `semantic` (косинус) |
| `characteristic` (имя свойства, только `actual`) | `lexical`, `semantic` |
| `value` (текст значения, только без `issue`) | `lexical`, `phrase` (`strict_word_similarity` + `<<%`, только для значений с ≥4 буквами), `semantic` |

Служебные настройки внутри транзакции: `hnsw.iterative_scan = 'strict_order'`, `hnsw.ef_search = 100`, `pg_trgm.similarity_threshold = 0.1`, `pg_trgm.strict_word_similarity_threshold = 0.4`. Комментарий объясняет выбор: «Bound distance-ordered row queries allow HNSW to participate, unlike MAX/GROUP BY scans».

Слияние — **Reciprocal Rank Fusion** с весами: `score += (2 если поле=position иначе 1) / (60 + rank)` (`storage.py:260`). Имя товара вдвое важнее свойства или значения.

Цикл расширения (`storage.py:246-255`): если уникальных кодов меньше `max(100, limit*8)`, лимит строк удваивается до 10 000; при упоре в потолок ставится флаг `field_scan_capped` — то есть **усечение видно в доказательствах**, а не происходит молча.

Диверсификация (`storage.py:271-281`): кандидаты группируются по имени и выбираются **round-robin** — сначала по одному лучшему на каждое имя, потом вторые, и т.д. Это чинит наблюдавшуюся проблему, когда «несколько версий одной куртки или стула занимали весь шортлист» (`experiments/pipeline-explanation.md`).

Для `value`-совпадений сохраняется детальное свидетельство: код и имя характеристики, `value_id`, текст, похожесть (`storage.py:261-267`) — это и есть «обоснование» для пользователя.

Отдельно: `retrieval.truncated=true` означает лишь, что часть позиций не вошла в шортлист; **recall это не устанавливает** — формулировка явно зафиксирована в README.

### 8.4 Различение семейств и выбор вопроса

`resolve_families` — механизм «поэтапного сужения», который в `main` существует, но **внутри одного прогона**, а не между запросами.

Для каждого родительского шаблона, чьё имя подтверждено моделью: берётся полный набор детей (включая **не вошедших в шортлист** — из `get_family_splits`), и для каждой различающей характеристики вычисляются исходы по всем её вариантам. `conflict` → дети этого варианта исключаются из `viable` и соответствующие кандидаты помечаются `rejected` с причиной «Подтверждённая характеристика исключает эту ветвь семейства». `matched` → характеристика считается `observed`.

Характеристика помечается `unresolved`, если при нескольких живых детях домены расходятся или покрыты не все дети. Тогда формируется вопрос «Укажите «\<имя\>»: вариант1 / вариант2 / …» (список вариантов — только если их ≤8).

Выбор **лучшего** вопроса — детерминированный, без ML (`pipeline.py:480-483`): кортеж `(не обязательна, покрытие неполное, доля наибольшей группы, числовая, имя, код семейства)` минимизируется. То есть приоритет: обязательные → наиболее сбалансированно делящие множество → нечисловые. Комментарий фиксирует: «Required first, then the most balanced partition; no name-based code grouping».

Семейство считается `resolved`, только если инференс полон, остался ровно один кандидат со статусом `supported` и все различающие характеристики разрешены.

### 8.5 Путь «CSV-пакет»

`CsvBatchPanel.vue` + `useCsvBatch.ts`: drag&drop или выбор файла → `parseTable` (с валидацией; пустой файл → «В файле нет строк с описаниями») → предпросмотр первых двух строк → последовательный прогон: для каждой строки сначала `spellCorrect` (LanguageTool, ошибка глушится и поднимает баннер), затем `api.analyze` с **одним ретраем через 1.5 с только на 503** (`useCsvBatch.ts:33-35, 114-122`). Результаты появляются по мере готовности (стриминг в UI), прогресс-бар, отмена через `AbortController`.

Последовательность не случайна: бэкенд всё равно не принял бы параллельные запросы (model lock → 503), поэтому фронт не создаёт бессмысленную нагрузку. Ретрай именно на 503 — прямое соответствие контракту `Retry-After`.

Для CSV существует `data/test.csv` — одна строка с реальным описанием аккумуляторной отвёртки Bort и pipe-разделёнными характеристиками. Это **пример входных данных**, а не маркированный тестовый набор: эталонного кода КТРУ в нём нет.

## 9. Внешние модели и ML-контракт

### 9.1 Классификатор «System One» (`jiwo-4b`)

Примитив — **попарное оценивание выбора**, а не генерация. Запрос:

```json
{
  "model": "jiwo-4b",
  "state": "<описание пользователя>",
  "questions": {
    "<id>": { "type": "choice", "instructions": "...", "criteria": { "<вариант>": "<описание>" } }
  }
}
```

Ответ: `answers.<id> = { choice, confidence, probabilities }`. Эндпоинты: `GET /health`, `POST /v1/systemone`. Это **не** OpenAI-совместимый chat-completions API и **не** альтернативный OpenJev `/score` (`experiments/README.md` §5). Поддерживаются также вопросы типа `noul`, но пайплайн использует только `choice`.

Четыре статуса факта (`classifier_experiments.py:34-39`): `supported` / `contradicted` / `unknown` / `conflicting`. Формулировки на русском и принципиально различают «не указано» и «отрицается»: «Отсутствие упоминания не означает отрицание». Для числовых вопросов добавляются варианты-идентификаторы фрагментов плюс `unknown` и `conflicting`.

Инструкции модели содержат явные guardrails: «Не переноси свойства упаковки на товар», «Не додумывай отсутствующие данные», «Не подставляй число только из-за совпадения единицы измерения».

### 9.2 meow-embed (`google/embeddinggemma-2`)

`POST /embed` с `{texts, dense_model_id, dense_prompt}`; ответ — base64 float32 матрица с `shape`, `model_id`, `dtype`, `encoding`. Клиент (`embedding_retrieval.py:94-124`) декодирует, проверяет длину байтов, соответствие модели, нормализует векторы до единичных.

Обязательные префиксы (`EMBEDDING_QUERY_PROMPT` / `EMBEDDING_DOCUMENT_PROMPT`) содержат **значащий завершающий пробел**, что отдельно отмечено в `.example.env`: «Quotes preserve the trailing space required by these model prefixes». Размерность жёстко 768 — это CHECK в БД (`embedding_configs.dimensions = 768`) и константа `DIMENSIONS` в `retrieval.py:9`.

Документы для эмбеддинга формируются с контекстом (`scripts/embed_db.py:26-49`): позиция — только имя; характеристика — «имя товара\nимя свойства»; значение — «имя товара\nимя свойства\nтекст значения». Встраиваются только `actual`-характеристики и значения без `issue`; **числовые диапазоны не эмбеддятся**.

### 9.3 Что известно о качестве моделей

Из `experiments/README.md` §21 — обзор 10 полных прогонов, 84 HTTP-запроса, 189 вопросов:

| Эксперимент | Результат | Практический смысл |
|---|---|---|
| smoke | 15/16 (факты 11/12, маршрутизация 4/4) | Простые кейсы проходят; пример с `conflicting` провален |
| numeric | 5/6 на обоих повторах | Принадлежность числа зарядному устройству работает; `0,018 кВ` по-прежнему не выбирается |
| slots | 7/9 (ручная разметка) | Одна батарея и угловая конструкция **выдуманы** |
| facts | 20/20 в каждом полном скане | Независимые проверки консервативны на близких примерах дрелей |
| progressive | 78/80 (ручная разметка) | Высокая точность скрывает один выдуманный факт |
| order | 3/3 | tested вопрос переносит обратный порядок вариантов |

**Порог 0.8 не откалиброван**, и это продемонстрировано на конкретных числах: «Нужна дрель → ударный режим = Да» получает 0.848 (**выдуманный факт проходит**), а «аккумуляторная дрель с реверсом, без ударного режима → ударный режим = Нет» получает 0.690 (**верный факт отбрасывается**). Тот же факт в другом описании — 0.922 и 0.974. Вывод документации: «Changing the wording changes the scores … The threshold alone cannot provide reliable extraction».

Все приведённые оценки — **диагностические фикстуры ручной разметки, не held-out бенчмарк**. Это явно оговорено: `manifest.diagnostic_not_held_out = true` пишется в каждый артефакт (`service.py:105`), а `Report.snapshot` содержит `threshold_uncalibrated`. Такая честность в коде — редкость и сильная сторона проекта.

## 10. Конфигурация

Единый источник — `.env` в корне репозитория, загружается `python-dotenv` из `experiments/config.py:14-19` **независимо от cwd**. Приоритет: переменные процесса > `.env` > CLI-флаги.

`Settings` — frozen dataclass с `default_factory`, то есть все переменные читаются при создании, а не при импорте модуля. `env(name)` **бросает исключение** при отсутствии обязательной переменной: «Missing required variables fail with a setup message rather than silently choosing a service». `__post_init__` (`config.py:79-120`) валидирует ~30 инвариантов: схема URL, конечность и положительность таймаутов, `1 ≤ pool_min ≤ pool_max`, порт 1–65535, `top_k` 1–32, `chunk_size` 1–8, `batch_size` 0 или 1–64, `threshold` конечный в [0,1], непустые ID моделей, `HISTORY_MAX_ITEMS` 1–50, схема `redis://`/`rediss://`.

Относительные пути разрешаются **от корня репозитория** (`env_path`, `config.py:34-36`) — поэтому сервисы можно запускать из любой директории.

`.env` в git **не** попадает и **никогда не коммитился** (проверено: `git check-ignore` → `.gitignore:248`, `git log --all -- .env` пуст). Шаблон `.example.env` содержит только localhost-адреса. Секретов в отслеживаемых файлах не обнаружено.

Итог: воспроизводимая загрузка каталога из свежего checkout **не работает** без ручной раскладки файлов. Фактически команда использует либо уже наполненную удалённую БД, либо `db_seed.sh restore` из общего дампа, которого в репозитории нет.
